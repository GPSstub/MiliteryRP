# 군용 메신저 설정과 영구 저장

## 사용 방법

오른쪽 `통신` 버튼 또는 M키로 메신저를 엽니다. 왼쪽 채널 목록의 `+`는 채널 생성 권한이 있고 저장소 로딩이 끝난 사용자에게 표시됩니다. 이름을 입력하는 모달에서 생성합니다. 설정 버튼에서는 채널, 역할, 사용자, 저장 상태를 같은 사이드바 구조로 관리합니다. 좁은 화면에서는 설정 탐색이 상단 탭으로 바뀝니다.

- 채널: 선택 → 이름 변경 / 삭제 / 역할별 읽기·쓰기·관리 허용. 기본 네 채널은 삭제할 수 없습니다.
- 역할: 영문 ID와 표시 이름으로 생성 → 선택 → 표시 이름·개별 권한 수정 또는 삭제. 기본 member/officer/operator/muted 역할은 보호됩니다.
- 사용자: 역할 탭에서 역할 선택 → 현재 접속자에게 부여/제거. 오프라인 사용자는 숫자 UserId로 배정할 수 있습니다. 배정은 재접속·서버 재시작 후 유지됩니다.
- 삭제는 확인 모달을 거칩니다. 역할 삭제는 모든 배정과 채널 ACL에서도 해당 역할을 제거합니다.
- 사용자 작성 이름은 생성/변경 시와 서버에서 불러온 뒤 서버 TextService 필터를 거쳐 표시합니다. 실패 시 원문을 보여 주지 않습니다. 이름 생성·변경은 사용자별 60초 간격입니다.

## 권한 의미

최종 검사는 서버에서 합니다. 클라이언트 속성·버튼 숨김은 편의 표시이며 권한 증명이 아닙니다.

- 제작자 UserId `1153125948`은 통신망 관리 권한을 유지합니다. 군대 어드민 기능과 메신저 역할은 별개입니다.
- 모든 사용자는 member 역할을 갖습니다. 기존 main의 동작을 유지하여 소위 이상(RankOrder 11 이상)은 officer 역할을 자동으로 갖습니다. 역할 자동 연결을 바꾸려면 `MessengerState.rolesFor`를 수정합니다.
- 역할의 허용은 합산(OR)됩니다. 비공개 채널은 member 읽기를 해제하고 원하는 역할에 읽기를 허용하세요. 다른 역할의 허용을 무효화하는 Discord식 명시적 deny 덮어쓰기는 구현하지 않았습니다.
- 읽기가 있어야 쓰기가 가능합니다. 쓰기는 전역 SEND_MESSAGES도 필요하고, 공지·지휘 채널은 기존 특수 쓰기 권한도 필요합니다. muted는 제작자를 제외한 발언을 제한합니다.
- MANAGE_SETTINGS는 모든 채널 관리 권한을 포함합니다. 채널 manage ACL은 해당 채널만 위임합니다. 채널 삭제에는 DELETE_CHANNELS도 필요합니다.
- 역할 관리자는 자신에게 없는 전역 권한을 부여하거나 자신보다 높은 권한을 가진 역할을 수정·배정·제거할 수 없습니다.
- 부대 채널은 기존 Unit 또는 팀이 일치하는 사용자끼리만 전달합니다. 이 기능 때문에 팀을 새로 생성하지 않습니다.
- 권한을 잃으면 서버의 TextSource를 제거하고 클라이언트는 해당 채널의 메모리 기록을 비웁니다. 이미 받은 내용을 원격으로 회수할 수 있는 것은 아닙니다.

## 데이터와 동시 수정

`MessengerState`: 순수 권한·변경 규칙 및 스키마 검증.
`MessengerStoreCore`: 저장 어댑터에 의존하는 트랜잭션 로직.
`MessengerStore`: 실제 DataStoreService와 MessagingService 연결.
`MessengerRuntime`: TextChannel 수명·참여자·전달 권한 및 메타데이터 필터링.

저장소는 schema 1 문서 한 개이며 채널, 표시 이름 원문과 작성자 ID, 역할, ACL, 사용자 ID별 역할 배정, revision, 최근 작업 영수증을 함께 저장합니다. 메시지 내용·채팅 기록·군대 계급·무적/비행 상태는 저장하지 않습니다. main의 기존 메모리 전용 설정을 과거 서버에서 복구할 수는 없으며, 최초 저장은 기본 설정에서 시작합니다.

- 실제 서버: `MilitaryMessenger_Config_v1` / `configuration`
- Studio: `MilitaryMessenger_Config_Dev_v1` / `configuration`
- 추가 채널 최대 24개(기본 4개 포함 총 28), 역할 총 30개, 역할 배정 사용자 1,000명, JSON 1 MB 제한. 작은 통신망의 저빈도 관리 설정을 위한 구조입니다. 대규모 조직은 사용자 배정 키를 분리하는 별도 마이그레이션이 필요합니다.

클라이언트가 본 revision을 보내고 서버가 UpdateAsync 콜백 안에서 최신 저장 데이터의 revision과 권한을 다시 검사합니다. 둘이 다르면 변경을 거부하고 다시 읽습니다. 오래된 전체 스냅샷을 SetAsync로 덮어쓰지 않습니다. 로컬 저장도 직렬화하고, 최대 세 번 지수 백오프 재시도 시 같은 작업 ID를 사용합니다. 저장 후 응답 유실은 저장 문서의 영수증으로 중복 반영을 피합니다. 끝내 응답을 확인하지 못하면 성공으로 표시하지 않고 재조회합니다.

저장 완료 전에는 메모리 설정과 채널 권한을 바꾸지 않습니다. 시작 시 읽기 실패·지원하지 않는 스키마·손상 데이터는 관리 변경과 메신저 전달을 잠급니다. 기본 설정을 실제 데이터 위에 저장하지 않습니다. 아직 저장되지 않은 수정 큐가 없으므로 종료 시 캐시 전체를 저장하는 BindToClose 작업도 없습니다. 성공으로 응답한 변경은 이미 저장됐습니다.

서버 간에는 revision 알림만 MessagingService로 전송합니다. 알림 누락·순서 변경은 30~40초 주기 재조회로 회복합니다. 알림 구독 실패도 재시도합니다. 이것은 강한 실시간 동기화가 아니며 다른 서버의 권한 회수는 그 서버가 변경을 읽을 때 반영됩니다. 다른 서버에서 이미 읽은 채팅은 회수되지 않습니다. 메시지 자체는 현재 서버 안에서만 전달합니다.

## Roblox 통신 안전성

메시지는 클라이언트 `TextChannel:SendAsync` → Roblox TextChatService → 수신자별 `MessageReceived`만 사용합니다. 채팅 내용을 RemoteEvent로 재전송하거나 별도 DataStore에 보관하지 않습니다. 서버의 ShouldDeliverCallback은 발신자의 쓰기와 수신자의 읽기 권한을 검사하며 yield하지 않습니다. AddUserAsync가 참가할 수 없다고 판단한 이용자에게 가짜 TextSource를 만들지 않습니다. Roblox 필터링·이용자 통신 제한을 우회하지 않습니다.

RBXGeneral/RBXSystem, 기본 채팅 입력, 계급 명령어는 변경하지 않습니다. GeneralBubbleChat은 기존대로 RBXGeneral의 성공 메시지에만 말풍선을 표시합니다. RP_ 채널은 군용 메신저에서 처리합니다. 모든 입력은 RichText가 아닌 텍스트로 렌더링합니다.

## 비공개 테스트 게임에서 실제 저장 테스트

1. 변경된 `MilitaryRP.rbxlx`를 열거나 `default.project.json`으로 소스를 동기화합니다. 이미 열린 Studio 창은 디스크 파일 변경을 자동으로 읽지 않을 수 있습니다. 저장할 작업을 보존한 뒤 다시 여세요.
2. 운영 게임과 **다른 테스트 경험(유니버스)** 으로 `File → Publish to Roblox As`로 게시합니다. Creator Dashboard에서 접근 범위를 비공개로 유지하세요. 이 작업에서 게임을 게시하거나 공개 범위를 바꾸지는 않았습니다.
3. `File → Experience Settings → Security → Enable Studio Access to API Services`를 켜고 저장합니다. Studio 버전에 따라 설정 이름·위치가 조금 다를 수 있습니다. Studio 테스트도 Roblox 데이터에 접근하므로 운영 경험에서 켜지 마세요.
4. Play 후 메신저 설정의 저장 상태가 연결 완료인지 확인합니다. 로딩 실패 상태에서는 수정이 잠기는 것이 정상입니다.
5. 채널과 역할을 생성하고 사용자에게 배정한 뒤 Play를 멈추고 다시 시작해 복원을 확인합니다. 채널·역할 이름 생성/변경 사이에는 60초 기다립니다.
6. 실제 서버 두 개에서 같은 revision의 설정을 동시에 바꾸어 하나가 충돌로 거부되고, 새로고침 후 다시 수정할 수 있는지 확인합니다. 계정별 Roblox 채팅 제한과 필터링은 실제 계정 2개 이상으로 검증합니다.
7. 읽기 권한 회수, muted, 재접속, 다른 부대, 계급 `/계급 대위`, 머리 위 계급, 기본 채팅 말풍선, RP 메시지 말풍선 분리를 확인합니다. Studio 1인 Play만으로 계정 간 필터링을 검증했다고 간주하지 마세요.

## 2026-10-20 UI 개선

- 넓은 화면은 채널 / 대화 / 접속자 3열, 작은 화면은 채널 버튼으로 목록을 별도로 표시합니다.
- 채널 이름 검색과 현재 세션에 수신된 메시지·작성자 검색을 제공합니다. 이전 서버 메시지를 검색하거나 메시지 본문을 영구 저장하지 않습니다.
- 새 메시지는 현재 스크롤을 맨 아래로 이동시키지 않습니다. 전송한 본인의 메시지도 같습니다. `새 메시지 N개 · 확인하기 ↓`를 직접 눌러야 이동하고 해당 채널의 미확인 수가 해제됩니다.
- 채널별 스크롤과 임시 입력은 현재 접속 중에만 보관합니다. 채널 접근 권한이 없어지거나 부대가 바뀌면 관련 기록을 지웁니다.
- 메시지는 증분 추가하며 채널당 최근 80개만 유지합니다. 오래된 행이 제거될 때는 남아 있는 읽기 위치를 보정합니다. 보관 한도를 넘은 메시지는 복구할 수 없습니다.
- 설정은 채널·역할·사용자·저장 상태로 구분하고, 권한은 텍스트가 함께 있는 토글로 표시합니다. 사용자 화면에서 부여할 수동 역할을 직접 선택할 수 있습니다.
- 검색은 이미 TextChatService가 전달한 필터된 메시지에만 적용합니다. 서버 ACL, 통신 제한, 기본 채팅/말풍선 분리는 유지합니다.

### 내 메신저 설정

연속 메시지 묶기, 메시지 간격, 아바타, 접속자 목록, 새 메시지 알림, 글자 크기 14/16/18을 설정합니다. 현재 접속 중 나에게만 적용되며 재접속 시 기본값으로 초기화됩니다. 알림을 꺼도 미확인 개수는 유지합니다. 강제 맨 아래 이동은 추가하지 않습니다. 메신저가 열려 있는 동안 기본 Roblox 플레이어 목록을 숨기고 닫으면 이전 상태를 복원합니다.

### 서버 설정

- 카테고리 최대 12개 생성·이름 변경·삭제·순서 변경. 채널 배치/순서 변경, 카테고리 접기/펼치기.
- 카테고리 권한에 동기화된 채널은 공유 권한을 사용합니다. 해제하거나 카테고리를 삭제할 때 현재 권한을 복사해 채널을 보존합니다. 삭제 버튼은 확인 창을 거칩니다.
- 읽기·쓰기·관리 권한에 허용/상속/거부를 추가했습니다. `상속`은 추가 덮어쓰기를 제거해 기존 ACL 기본값을 유지합니다. 카테고리 동기화 중에는 개별 권한을 편집할 수 없습니다.
- 권한 계산: 기존 ACL 허용 합산 → 일반 사용자(member) 명시적 덮어쓰기 → 나머지 보유 역할의 거부 합산 → 허용 합산. 소유자·통신망 관리 권한, 발언 제한, 지휘·공지·부대 채널의 기존 추가 검증도 유지합니다. Discord의 멤버별 덮어쓰기·모든 권한 비트·역할 우선순위를 완전히 복제한 것은 아닙니다.
- 권한, 배치, 순서 변경은 최대 40개를 임시 보관하며 `변경 저장`에서 한 트랜잭션으로 저장합니다. 실패·리비전 충돌 시 임시 입력을 유지합니다. `초기화`는 최신 서버 스냅샷으로 되돌립니다. 이름 생성/변경/삭제 및 역할 부여는 기존 확인/실행 흐름을 유지하며 임시 변경이 있으면 먼저 저장하거나 초기화해야 합니다.
- 화면의 백그라운드 조회와 변경 요청 제한을 분리했습니다. 실제 저장소 강제 새로고침은 관리자 전용이며 전체 서버 5초 제한을 적용합니다.

### 저장 호환성과 배포

스키마 1을 계속 읽고, 변경 저장 시 스키마 2로 올립니다. 기존 계급·역할·배정·채널을 초기화하지 않습니다. 구버전 서버는 스키마 2를 읽을 때 통신망을 잠그므로 배포 후 기존 서버를 최신 코드로 교체해야 합니다. 구버전으로 되돌리려면 스키마 2를 이해하는 코드 또는 별도의 데이터 복구 절차가 필요합니다. 개발/실서비스 저장소 분리는 그대로입니다.

Studio 개발 저장소에서 `부대 통신` 카테고리를 생성하고 전체/공지 채널을 배치한 후, 테스트 서버 재시작으로 revision 3의 복구를 확인했습니다. 이 배치는 개발 저장소에만 남아 있으며 실서비스 설정을 대신하지 않습니다. 사용자 대화는 저장하지 않습니다.

검증: 기존 저장/권한 84개, 설정 확장 63개, 대화·환경설정 UI 19개, 설정 편집 UI 13개 검사. UI 실패 테스트는 가짜 로컬 RemoteFunction 어댑터를 사용하므로 실제 장애 주입과 구분됩니다. 실제 다중 사용자 통신·운영 서버 간 전파·물리 모바일 기기는 추가 QA 대상입니다.
